# 開発フロー詳細（.codex/flow.md）

> このフローは **Codex** での使用を前提とする（`.codex/agents/` に定義したサブエージェントへの工程委譲を利用）。

> **【このフローが部分的に適用できないプロジェクトタイプ】**
> 以下の場合は該当フェーズの手順を次のように読み替える（注記がないフェーズは共通手順のまま）：
> - **Chrome Extension（Manifest V3）**：.env 不可（Phase 7：APIキーは chrome.storage / options page 経由）・
>   Phase 3：popup / options page を SCR として扱う・Phase 8：ウェブストア提出（専用手順あり）
> - **モバイルアプリ（React Native / Flutter 等）**：Phase 3：モックは Expo Go / Flutter プレビューで確認・
>   Phase 7：実機/シミュレータでの動作確認を機能検証に含める・Phase 8：deployment-runner は使わずストア提出手順に読み替える
> - **SwiftUIネイティブアプリ（iOS / macOS）**：.env 不可（Phase 2：architecture.md の環境変数セクションは
>   「秘密情報の管理方法（Keychain / xcconfig / Info.plist）」に読み替え・Phase 7：APIキー等は Keychain 経由）・
>   Phase 3：モックは SwiftUI の View として実装し Xcode Previews / シミュレータで確認（SCR-XX = 1 View に対応）・
>   Phase 7：テストは XCTest（UIテストは XCUITest）を `xcodebuild test` で実行し、
>   実機/シミュレータでの動作確認を機能検証に含める・
>   Phase 8：deployment-runner は使わず配布形態で読み替える（自分のみ＝ローカルビルド or Developer ID 配布 /
>   公開＝TestFlight → App Store 提出。Xcode・macOS・SDK のバージョン互換はグローバルAGENTS.mdの規定どおり
>   記憶で断言せず公式ドキュメントをWeb検索して確認する）

## オーケストレーション構成（メイン＋サブエージェント）【全フェーズ共通】

本フローは「指示役のメインエージェント＋工程担当のサブエージェント」で進める。
サブエージェント定義は `.codex/agents/` に配置されている。サブエージェントは独立コンテキストで
動くため、前フェーズの会話を引きずらず、設計書・progress.md だけを正として動ける。

### 役割分担

- **メインエージェント（指示役）**：ユーザーとの対話（ヒアリング・成果物の承認確認・判断の相談）、
  フェーズ進行の判断、サブエージェントへの委譲、progress.md の更新を担う。
  **設計書のドラフト・実装・テスト等の重い作業は自分では行わず、必ずサブエージェントに委譲する。**
- **サブエージェント（工程担当）**：委譲されたタスクを独立コンテキストで実行し、
  成果物と「要確認事項」をメインに返す。**ユーザーへの確認はメインを経由する。**

### モデル・工数の設定

| 役割 | モデル | 工数（effort） | 設定方法 |
|---|---|---|---|
| メインエージェント | `gpt-5.6-sol` | high | `.codex/config.toml` |
| mock-builder・implementer・debugger・code-reviewer | `gpt-5.6-sol` | high | `.codex/agents/*.toml` |
| その他のサブエージェント | `gpt-5.6-terra` | high | `.codex/agents/*.toml` |

### サブエージェント一覧

| agent名 | 担当 | 主に使うスキル |
|---|---|---|
| researcher | Phase 1 Step 2〜3（市場・技術調査） | Web検索 / pre-implementation-check |
| design-writer | Phase 2（設計書5種のドラフト）・Phase 4/運用フェーズの設計書更新・**Phase 8以降のREADME作成/更新** | requirements-writer 等の writer 系 / readme-writer + humanizer-ja |
| mock-builder | Phase 3（モック実装）・Phase 4（モック再生成） | mock-frontend-design |
| detailed-designer | Phase 5（詳細設計） | detailed-design-writer |
| consistency-checker | Phase 6（整合性チェック） | consistency-checker |
| implementer | Phase 7 Step A（実装）・Step C.5（リファクタリング） | implementation-runner / refactoring-runner |
| tester | Phase 7 Step B（テスト） | testing-runner |
| code-reviewer | Phase 7 Step D（コードレビュー） | code-reviewer |
| debugger | Phase 7 Step C（FAIL修正）・随時のバグ修正 | debug-runner / debugging-approach |
| deployer | Phase 8（デプロイ） | deployment-runner |

### 委譲の原則

1. メインは委譲プロンプトに **タスク内容・参照ファイルのパス・ヒアリング結果や決定事項・成果物の出力先** を
   明記する（サブエージェントはメインの会話履歴を持たないため、必要な情報はすべてプロンプトか参照ファイルで渡す）
2. サブエージェントは不明・曖昧・矛盾を発見したら**推測で進めず**、作業を止めて「要確認事項」として返す。
   メインがユーザーに確認し、回答を添えて再委譲する。
   **サブエージェントから要確認事項を受け取ったら、メインはその場で progress.md の
   「未回答の要確認事項」欄に転記する**（すぐユーザーに聞く場合も転記する。会話の中に置き去りにしない）。
   ユーザーの回答が出たら「直近の決定事項」に回答を記録し、表から行を消す
3. progress.md の更新は**メインのみ**が行う（サブエージェントは触らない）
4. 設計書等の成果物 md は、サブエージェントのドラフト完成後に**メインがユーザーに提示して承認を得る**（絶対ルール3）
5. メインは委譲結果の成果物を必ず自分で確認してから次に進む（サブエージェントの報告を鵜呑みにしない）
6. デプロイ等の取り返しのつかない操作は、**メインがユーザーの明示承認を得てから**「ユーザー承認済み」と
   明記して委譲する（明記がない場合、deployer は実行直前で停止する）

### Git コミット規律（メインが実施）

「フェーズの区切りでコミット」を次のとおり具体化する。コミットはメインが行う。
`progress.md` は必ずコミット前に更新し、対象成果物と同じコミットへ含める。

| タイミング | 必須/推奨 | メッセージ例 |
|---|---|---|
| Phase 0：ローカルGit初期化後 | **必須** | `chore: 開発フローを初期化` |
| Phase 0：GitHub・選択した夜間実行環境の確認後 | **必須** | `chore: Phase 0を完了` |
| 各フェーズの完了時 | **必須**（Phase 1も追跡対象の `progress.md` を含める） | `phase 2: 設計書5種を作成` |
| Phase 3〜4：モックの各デザイン案・反映1回ごと | **必須**（「前の案に戻りたい」に備える） | `mock: A案（ヴィブラント＆ブロック）` / `mock: フォーム位置を一覧の下へ` |
| Phase 7：FR実装の完了ごと・品質ループ1周ごと | **必須** | `feat: FR-01 イベント登録` / `fix: レビュー🟡2件対応` |
| 設計書の大きな更新後 | 推奨 | `docs: detailed_design セクション2更新` |
| 夜間・クラウド作業の開始前 | **必須**（開始点をコミットし、Cloud使用時はリモートへ同期） | `chore: 夜間作業前の状態を同期` |
| 夜間・クラウド作業の完了時 | **必須**（`codex/*` ブランチ） | `feat: FR-01を夜間実装` |

Push と PR の権限は次のとおり扱う：

- main への Push、初回 Push、PR のマージは毎回ユーザー承認を得る
- `codex/*` への Push と PR 作成は、Phase 0 で対象リポジトリを明示した継続許可が
  `progress.md` に記録されている場合だけ再確認なしで実行できる
- 継続許可がない場合はローカルコミットまで行い、Push・PR 作成を保留してユーザーへ報告する
- `git push --force` はブランチを問わず実行しない

デザイン案の比較・巻き戻しは `git log --oneline` → `git checkout <hash> -- src-mock/` で行えることを
ユーザーに案内してよい。

### 夜間・クラウド作業の安全ゲート

夜間または無人作業を開始する前に、メインは次を確認する：

1. 未回答の要確認事項がなく、作業範囲・完了条件・実行するテストが `progress.md` に記録されている
2. main の作業ツリーがクリーンで、開始点がコミット済みである。Codex Cloud使用時はGitHubへPush済みである
3. 実行環境を問わず `codex/{日付}-{短いタスク名}` ブランチを使う
4. ファイル削除、本番デプロイ、本番DB変更、main への反映をタスク範囲に含めない
5. ローカル Scheduled task の場合は専用 worktree を使い、Mac とデスクトップアプリを起動したままにする
6. 状態変更を伴う無人作業は1リポジトリにつき同時に1件とし、`progress.md` の競合を防ぐ

無人作業の完了時は、テスト、README 更新判定、`progress.md` 更新、コミットの順で実施する。
継続許可があれば `codex/*` へ Push して PR を作成し、main へはマージせず翌朝のレビューを待つ。

### /clear の扱い（保険）

通常はフェーズをまたいでも同一セッションのメインが進行を続ける（サブエージェントが独立コンテキストで
動くため、従来の「フェーズ境界で /clear」は不要）。ただし**メインのコンテキストが肥大化した場合の保険**として、
従来どおりフェーズ境界でセッションを乗り換えてよい。乗り換える場合は次の2点を確認してからセッションを終える：

1. このフェーズで確定した仕様・決定事項が設計書（`design/` 配下）または progress.md の「直近の決定事項」に
   **すべて書き出されている**こと（会話の中だけで決まった事項を残さない）
2. progress.md の「現在のフェーズ」「次のアクション」が更新済みであること

乗り換え後は AGENTS.md のセッション開始手順どおり progress.md を読んでから作業に入る。

## README の最新化ルール【全フェーズ共通】

README.md は設計書からの**派生成果物**（requirements / architecture / setup / business を
公開向けに要約したもの）。派生元が更新されても README が再生成されないと、README だけが
古い状態で取り残される。これを防ぐため以下を全フェーズ共通のルールとする。

### 担当

README.md の**作成・更新はすべて `design-writer` に委譲する**（初回作成・運用フェーズの更新とも）。
使うスキルは `readme-writer` → `humanizer-ja` の順で必ず両方通す（AI臭さを残したまま公開しないため）。
`deployer` は README を触らない（デプロイに専念する）。

### 更新トリガー表（該当したら README 更新は省略不可）

「大きな機能追加のときだけ」といった曖昧な判断はしない。次のいずれかに該当したら必ず更新する。

| 変更した内容 | 見直す README セクション | 派生元 |
|---|---|---|
| FR の追加・削除・変更 | 機能／使い方 | requirements.md |
| 異常系・エラーメッセージの変更 | よくある問題 | requirements.md |
| 技術スタック・依存パッケージの追加/更新 | 技術スタック／前提条件 | architecture.md |
| 環境変数の追加・削除・改名 | 環境変数／セットアップ | architecture.md |
| ディレクトリ構成の変更 | ディレクトリ構成 | architecture.md |
| 起動コマンド・セットアップ手順の変更 | セットアップ | setup.md / architecture.md |
| 外部サービスの設定手順の変更 | セットアップ（外部サービスの設定） | setup.md |
| 公開URL・デプロイ先の変更 | 概要／セットアップ | architecture.md |
| ライセンス・公開範囲の変更 | ライセンス | business.md |

### 更新のタイミング

| フェーズ | いつ更新するか |
|---|---|
| Phase 7 Step A（実装） | READMEが既に存在する場合だけ、環境構築手順・依存・環境変数の変更をarchitecture.md / setup.mdと同時に反映。未作成ならPhase 8の初回作成時に反映 |
| Phase 8（デプロイ） | 初回 README 作成。デプロイ実行前 |
| Phase 8以降（運用フェーズ） | 1タスク（バグ修正・機能追加）のコミット前。上表に1つでも該当したら必須 |

### 抜け漏れ検出（hook・自動）

`.codex/hooks.json` の PreToolUse hook（`.codex/hooks/readme-drift-check.py`）が
Codex が実行する `git commit` の直前に走り、ステージ済みファイルだけを確認する。
すべての変更コミットで `progress.md` が同じコミットに含まれない場合は停止する。
更新トリガー対象（`design/` 配下・依存ロックファイル・環境設定・セットアップファイル等）が
ステージ済みなのに README.md が同じコミットへ含まれない場合、コミットを停止する。
正確な判定ができない `git commit -a`、pathspec、`--only`、`--include` は使用せず、
対象を `git add` で明示的にステージしてからコミットする。
コミットはプロジェクトルートから単独で実行し、`cd`との連結、`bash -c`、複数コミットの連結、
`--git-dir`、`--work-tree`を使用しない。

`progress.md` の「READMEドリフト検出」が`無効`の Phase 0〜7 では hook は停止させない。
Phase 8 の初回 README 作成コミットで同項目を`有効`へ変更し、以降の更新漏れを検出する。
この hook は Codex の Bash 操作に対する補助ゲートであり、GUIやCodex以外のGit操作は対象外となる。
人がGUI等からコミットする場合も、同じ更新トリガー表を手動確認する。

警告が出たら上の更新トリガー表で該当セクションを確認し、更新してからコミットする。
hook が対象にしている変更は README 更新必須として扱い、例外判断で回避しない。

## Phase 0：Git・クラウド初期化

> **【担当】** すべてメイン。GitHub リポジトリの作成・初回 Push・Codex Cloud のアカウント接続は、
> ユーザーの承認または画面操作が必要。許可や接続結果は `progress.md` に記録する。

> 複製直後のプロジェクトでユーザーが`/start`だけを送信した場合、
> `AGENTS.md`の「`/start`の扱い」に従い、このPhaseのStep 1から開始する。

```
Step 1：プロジェクトルートと管理対象の確認

  このフォルダ（Develop Folder を複製してサービス名に変えたもの）をプロジェクトルートとする。

  {サービス名}/
  ├── AGENTS.md                 ← Git管理する
  ├── progress.md               ← Git管理する。秘密情報は書かない
  ├── .codex/                   ← Git管理する
  ├── .gitignore
  ├── design/                   ← Phase 2以降の設計書
  ├── src/ または app/          ← 実装コード
  └── README.md                 ← Phase 8で初回作成

  progress.md を次のように初期化する：
  - プロジェクト名・開始日を記入する
  - 現在のフェーズを「Phase 0：Git・クラウド初期化（進行中）」に更新する
  - 「次のアクション」を現在の Step に合わせる

Step 2：Git管理対象と秘密情報の確認

  - `AGENTS.md`、`progress.md`、`.codex/` が .gitignore 対象外であることを確認する
  - `.env`、秘密鍵、認証情報、一時レポート、`.codex/eval/results/` が除外対象であることを確認する
  - APIキー、パスワード、アクセストークンをファイルや progress.md に書かない

Step 3：ローカルGitの初期化

  - Git未初期化の場合だけ `git init -b main` を実行する
  - 既存リポジトリの場合は再初期化せず、現在のブランチ・履歴・remoteを確認する
  - 意図したファイルだけをステージし、`git status --short` と `git diff --cached` で確認する
  - `git check-ignore -v AGENTS.md progress.md .codex/config.toml` が何も返さないこと、
    `git check-ignore -v .env credentials.json` が除外ルールを返すことを確認する
  - progress.md を更新してステージしてから、`chore: 開発フローを初期化` で最初のローカルコミットを作る
  - README は Phase 8 で設計書から作るため、この初回コミットでは必須にしない

Step 4：GitHubリポジトリの作成・接続

  まず、今回GitHubに登録するか、ローカルGitだけで進めるかを確認する。
  GitHubを使う場合だけ、次もまとめて確認する：
  - GitHub のリポジトリ名
  - 公開範囲（既定は非公開。公開にする場合は理由を確認する）
  - リポジトリ作成と初回 main Push の承認
  - `codex/*` ブランチへの継続的な Push と PR 作成を事前許可するか

  「今回は使用しない」の場合は、GitHubリポジトリの作成・接続・Pushをスキップし、
  progress.mdにその決定を記録する。後日利用するときはPhase 0 Step 4〜6のみ再実行する。

  GitHubを使う承認後、利用可能な認証済み手段でリポジトリを作成または接続する。
  既存remoteを上書きせず、`git remote get-url origin` で接続先を確認してから初回 Push を行う。
  リポジトリURLと継続許可の回答を progress.md に記録する。認証情報は記録しない。

Step 5：夜間実行方式の確定

  次のどれにするかユーザーに確認し、progress.md に記録する：
  - Codex Cloud：GitHub上のブランチを使い、ローカルMacに依存せずバックグラウンド実行する
  - ローカル Scheduled task：専用worktreeを使う。Macとデスクトップアプリの起動が必要
  - 今回は使用しない：夜間実行を設定せず、通常のローカル開発だけで進める

  Codex Cloudを選ぶ場合はGitHub接続が必要。Step 4で「今回は使用しない」を選んでいた場合は、
  Step 4に戻ってGitHubの作成・接続承認を得る。

  main への直接Push・PRマージ・本番操作は、どちらの方式でも無人実行しない。

Step 6：選択した実行環境の接続確認

  「今回は使用しない」を選んだ場合：
  - このStepをスキップし、Codex Cloud環境・夜間実行方式ともに「今回は使用しない」と記録する

  Codex Cloudを選んだ場合：
  - ユーザーが Codex で GitHub を接続し、対象リポジトリへのアクセスを許可する
  - 対象リポジトリ用の Cloud environment を作成する
  - 対象ブランチをチェックアウトでき、AGENTS.md と progress.md を読めることを最小タスクで確認する
  - Phase 2 で技術スタックが確定するまでは、秘密情報や仮の依存設定を追加しない

  ローカル Scheduled taskを選んだ場合：
  - `codex/phase0-scheduled-smoke` ブランチの専用worktreeを作成する
  - ファイルを変更しない読取専用の確認タスクを1回登録し、worktree内のAGENTS.mdとprogress.mdを読めることを確認する
  - Macとデスクトップアプリを起動したままにする必要があることをユーザーへ説明する
  - worktreeパスと確認結果をprogress.mdへ記録し、Codex Cloud環境は「今回は使用しない」と記録する
  - 確認用タスクとworktreeを終了・削除する場合は、対象を示してユーザー承認を得る

Step 7：Phase 0の完了

  - progress.md のGit・クラウド状態をすべて更新する（未使用の項目は「今回は使用しない」で完了扱い）
  - 現在のフェーズを「Phase 1：調査（未着手）」へ更新する
  - 次のアクションを「Phase 1 Step 1：アイデアのヒアリング」に更新する
  - `chore: Phase 0を完了` でコミットする
  - GitHubを使う場合だけ、Phase 0完了状態を同期する2回目のmain Pushについて、
    改めてユーザー承認を得てから実行する
```

## Phase 1：調査

> **【担当】** Step 0・1・4 ＝ メイン ／ Step 2・3 ＝ `researcher` に委譲
> （委譲時は Step 1 のヒアリング結果を委譲プロンプトに含める）

```
Step 0：Phase 0完了の確認と progress.md の更新

  - Git初期化と、GitHub・夜間実行を「接続済み」または「今回は使用しない」のどちらかで
    progress.md に確定済みであることを確認する
  - 未完了なら Phase 1 を始めず、Phase 0 の該当Stepへ戻る
  - 現在のフェーズを「Phase 1：調査（進行中）」に更新する

  0. デザインの前提2点を整理してユーザーと確定する：

     - **脱却対象**：この分野のありがちなUIパターンを具体的に列挙し（例：角丸カード＋円形ゲージ＋

       ユーザーの既定の好みは「文字だけにせず、イメージ画像・イラストを多めに」）
     - **大胆さレベル**（無難〜革新的。ユーザーの指定がなければ「革新寄り」を推奨として提示する）
     - **トーン**（遊び心のある↔まじめ。ユーザーの既定の好みは「遊び心のあるアプリ」。

### Step 0：実装着手前のセットアップ内容の事実確認（メイン）

```
ユーザーに「setup.md に従って外部サービスのセットアップをしてください」と指示する前に、
必ず setup.md の内容が現時点でも事実として正しいかを確認・見直しする。
setup.md は Phase 2 で作成しており、外部サービスの仕様・料金・プラン・制限・手順は
その後変わっている可能性があるため、記憶を根拠に「正しいはず」で進めてはならない。
（setup.md の手順にユーザーを従わせる前の、最後の事実確認ゲート）

確認する観点：
  - 外部サービスの設定手順・画面名・メニュー位置（Google Cloud / Stripe / Apple / その他APIプロバイダー等）
  - 料金・プラン・無料枠・利用制限
  - 必要な環境変数・APIキーの取得手順とキー名
  - SDK・パッケージ・ランタイムのバージョン互換

確認方法（グローバルAGENTS.md「問題解決の原則」に従う）：

  - ライブラリ・SDK の仕様は公式ドキュメントで確認する

  - setup.md の記載と食い違いが見つかった場合は、先に setup.md を修正する（絶対ルール1）。
    修正内容はユーザーに提示して承認を得てから確定する（絶対ルール3）。
    環境変数に関わる修正は architecture.md との整合も確認する
  - 食い違いがなく内容が正しいことを確認できた場合は、その旨をユーザーに伝える
  - 事実確認（と必要な修正のユーザー承認）が完了してから、ユーザーにセットアップ実施を指示する

### Step A：実装

```
implementer サブエージェントに委譲する（implementation-runner スキルを使用）。
委譲プロンプトに対象FR・確定済みの決定事項を明記する。
参照ファイル：design/requirements.md / design/architecture.md / design/detailed_design.md

implementer が「要確認事項」を返した場合（仕様の不明・曖昧・矛盾で停止した場合）は、
メインがユーザーに確認し、回答を添えて再委譲する。

【仕様・型・セキュリティを確認する】
  外部ライブラリは公式ドキュメントを確認する。
  TypeScript は `tsc`、lint、テストを実行する。
  認証・入力・秘密情報を扱う場合は `security-and-hardening` を使用する。

【CLI ツール / パッケージの場合の動作確認】
  Web サーバーの起動確認（uvicorn / npm run dev 等）は不要。
  代わりに以下を確認する：
  - `python {entry}.py --help` または `{コマンド名} --help` が表示されるか
  - 主要コマンドを1つ手動実行してエラーなく動作するか

【実装中に環境構築手順が設計から変わった場合】
  venvの命名・起動コマンド・依存パッケージの追加など、環境構築手順に関わる決定が
  architecture.md / setup.md の記載と変わった場合は、変更した時点で両設計書を更新する
  （設計書とコードの乖離を残さないため）。
  **README.md が既に存在する場合は、同じタイミングで README も更新する**
  （「README作成時まで放置」は禁止。対象セクションは「README の最新化ルール」の更新トリガー表を参照）。

修正時（2回目以降）：
  test_report.md または code_review_report.md の内容を読んで
  修正が必要な箇所のみを実装し直す。
```

### Step B：テスト（tester に委譲）

```
tester サブエージェントに委譲する（testing-runner スキルを使用）。
UIありのプロジェクトでは、アプリ内ブラウザでの実機E2E確認が第一選択
（静的検証での代替は理由の明記が必要。tester の定義に規定済み）。
委譲プロンプト例：
「testing-runnerスキルを使って総合テストを実施してください。
 結果を test_report.md に書き出してください。
 FAILがある場合は原因の詳細も含めてください。」

以下のルールは tester が守る（tester の定義にも記載済み。委譲時に特記事項があれば添える）：

【実行環境のルール（毎回・全プロジェクト共通）】
  テストは venv の activate や特定シェルの PATH に依存しない形で実行・確認する。
  architecture.md の実行コマンド規約（例：./.venv/bin/pytest）をクリーンなシェルから
  直接実行して全件PASSを確認すること。CLIをサブプロセス起動するテストは、PATH上の
  コマンド名ではなく sys.executable -m 等の絶対解決で起動する。
  （activate済み環境でしか通らないテストは「PASS」とみなさない）

【テスト環境の確認（初回のみ）】
  E2Eテスト・統合テストを実施する前に、以下を確認する。

  外部サービス連携があるプロジェクトの場合：
    - テスト用アカウント・トークンが準備済みか確認する
    例：Slack Bot → テスト用 Workspace・テスト用 Bot Token
        外部API連携 → サンドボックス環境・テスト用 APIキー
    未準備の場合は setup.md のチェックリストを確認してセットアップしてから実施する。

  Webhook を持つプロジェクトの場合：
    - ローカルでの Webhook 受信ツールが準備済みか確認する
    （例：Stripe → Stripe CLI `stripe listen` / その他 → ngrok 等）

  外部 LLM API を使うプロジェクトの場合：
    - テスト時は実 API を叩かず jest.mock / unittest.mock 等でモック化する
    - モック困難な E2E だけ実 API を使用する。使用モデルと料金は実行直前に公式情報で確認する
    - テスト用の API キーに使用上限を設定しておくことを推奨する

  DBを使うプロジェクトの場合：
    - テスト用 DATABASE_URL が .env.test または .env.local に設定されているか確認する
    - テスト実行前にテスト用DBをリセットする
      ORM 使用時の例：
        Prisma → `npx prisma migrate reset --force`
        Alembic → `alembic downgrade base && alembic upgrade head`
      ファイルDB（SQLite）の場合：
        本番ファイルと別の一時DBを使う。既存ファイルの削除が必要ならユーザー承認を得る
```

### Step C：テスト結果の判定（メイン）

```
cat test_report.md で結果を確認する。

全PASS → progress.md のテスト結果を更新 → Step C.5 へ
FAILあり → debugger サブエージェントに委譲して修正（test_report.md のパスを渡す。
          debugger は再発防止テストを追加してから修正する＝定義に規定済み）
          → progress.md のブロッカーを更新 → Step B へ戻る

【無限ループ防止】
progress.md のループ回数を確認する。
同じFAILが3ループ連続で解決しない場合はユーザーに報告して中断する。
```

### Step C.5：リファクタリング（任意）

```
テストが全件PASSした後、コードレビューの前に必要と判断した場合に実施する。

判断基準（以下のいずれかに該当する場合に検討する）：
  ・コードの重複が目立つ
  ・Route Handler にビジネスロジックが漏れている
  ・関数が長すぎて責務が分かりにくい

実施する場合：
  implementer サブエージェントに「refactoring-runner スキルを使用したリファクタリング」として委譲する。
  リファクタリング完了後は必ず Step B（テスト）に戻り、動作が変わっていないことを確認する。

不要と判断した場合：
  このステップをスキップして Step D へ進む。
```

### Step D：コードレビュー（code-reviewer に委譲）

```
code-reviewer サブエージェントに委譲する。委譲プロンプト例：

「code-reviewerスキルを使って実装コードをレビューしてください。
 参照ファイル：design/requirements.md / design/architecture.md / design/detailed_design.md
 レビュー対象：src/ または app/ 以下の全実装ファイル
 UIありのプロジェクトでは、モック（src-mock/）とデザイン方針に対する
 ビジュアル忠実度（見た目・演出の劣化がないか）も観点に含めてください。
 結果を code_review_report.md に書き出してください。

 【静的解析・セキュリティ観点】
 - プロジェクトの lint・型チェック・静的解析結果をレポートに含めること
 - 必要に応じて `security-and-hardening` スキルを使用すること」
```

### Step E：コードレビュー結果の判定（メイン）

```
cat code_review_report.md で結果を確認する。
progress.md のループ回数・レビュー結果を更新する。

🔴あり → implementer に委譲して修正 → Step B へ戻る
        （code-reviewer が自動修正済みの場合は Step B へ直接戻ってよい）
🟡あり → ユーザーに提示 → YES なら implementer に委譲して修正 → Step B へ / NO なら次へ
🔴ゼロ → ループ終了 → progress.md の現在のフェーズを「Phase 8」に更新 → Phase 8 へ
```

## Phase 8：デプロイ

> **【担当】** デプロイ作業 ＝ `deployer` に委譲 ／ README の作成・更新 ＝ `design-writer` に委譲 ／
> デプロイ実行の承認取得・README のユーザー確認 ＝ メイン
>
> **本番デプロイは取り返しのつかない操作。メインが必ずユーザーの明示承認を得てから、
> 委譲プロンプトに「ユーザー承認済み」と明記して deployer に委譲する**（明記がない場合 deployer は実行直前で停止する）。

```
【README の作成・更新（デプロイ実行より先に行う）】
  design-writer に委譲する（deployer は README を触らない）。
  - README.md が未作成 → 新規作成
  - README.md が既にある → 「README の最新化ルール」の更新トリガー表に照らして差分更新する
    （前回デプロイ以降に変わった設計書のセクションを反映。ゼロから作り直さない）
  - 初回作成時は progress.md の「READMEドリフト検出」を `有効` へ変更し、READMEと同じコミットへ含める
  使用スキル：readme-writer → humanizer-ja の順に必ず両方通す
  参照ファイル：design/requirements.md / design/architecture.md / design/setup.md / design/business.md
  完成後はメインがユーザーに提示して確認を取る（絶対ルール3）。

architecture.md のホスティングセクションからデプロイ形態を確認して実施する。

【ローカル実行のみ（デプロイなし）の場合】
  business-writer のデプロイ形態A（個人利用のみ）等で、ホスティングが「なし」のプロジェクトが対象。
  deployment-runner は使用しない。以下のみ実施する：
  - README.md を作成・更新する（上記【README の作成・更新】と同じ。design-writer に委譲）
  - setup.md の動作確認チェックをローカルで最終実施する
  - progress.md の現在のフェーズを「Phase 8（完了・ローカル運用）」に更新し、運用フェーズへ移行する

【デプロイ前の互換性チェック】
  以下の組み合わせは非互換のため、architecture-writer の段階で代替を検討する：
  - SQLite（ファイルDB）× Vercel / Railway 等の PaaS
    → PaaS はエフェメラルなファイルシステムのため、デプロイのたびにデータが消える
    → PostgreSQL / MySQL 等のマネージドDBに切り替えることを推奨する

【サーバーデプロイ（Vercel / Railway / GCP 等）の場合】
  deployment-runner スキルを使用する。

  デプロイ前：
    □ 全テストPASS
    □ ローカルビルド成功
    □ 環境変数の棚卸し完了
    □ DBを使うプロジェクトの場合：本番DBのマイグレーション実施
        （例：Prisma → `npx prisma migrate deploy` / Alembic → `alembic upgrade head`）

  デプロイ後：
    □ setup.md の動作確認チェックを本番URLで実施
    □ 外部サービスの Webhook URL を本番 URL に更新
    □ OAuth を使うプロジェクトの場合：各プロバイダーの承認済みリダイレクト URI に本番 URL を追加

【パッケージ配布（PyPI / npm 等）の場合】
  deployment-runner スキルは使用しない。以下を手動で実施する。

  公開前：
    □ 全テストPASS
    □ バージョン番号を更新（pyproject.toml / package.json）
    □ CHANGELOG / README を更新（README は design-writer に委譲。更新トリガー表で対象セクションを確認）
    □ 認証情報（APIトークン）が準備済みか確認

  公開：
    PyPI → `python -m build && twine upload dist/*`
    npm  → `npm publish`

  公開後：
    □ インストールして動作確認（例：`pip install {パッケージ名}` → コマンド実行）

【Chrome Extension（Manifest V3）の場合】
  deployment-runner スキルは使用しない。以下を手動で実施する。

  公開前：
    □ 全テストPASS
    □ manifest.json のバージョン番号を更新
    □ API キー等の機密情報が chrome.storage または options page 経由で設定される設計か確認
       （.env は Chrome Extension では使用不可）
    □ `zip -r extension.zip . --exclude='.git/*' --exclude='node_modules/*'` でパッケージ化

  公開：
    Chrome Developer Dashboard (chrome.google.com/webstore/devconsole) でアップロード・審査提出

  公開後：
    □ Chrome ウェブストアからインストールして動作確認
```

### フロー振り返り（Phase 8 完了時にメインが必ず実施）

デプロイ（またはローカル運用への移行）が完了したら、運用フェーズに入る前に `flow_retrospective.md` を
プロジェクトルートに作成してユーザーに提示する（進捗・レポート類と同じくユーザー承認は不要だが提示は必須）：

- **詰まった点**：要確認事項が多発した工程・手戻りが起きた箇所・サブエージェントが迷った指示
- **効いた仕組み**：品質・スピードに寄与したフロー/スキル/エージェント定義
- **Develop Folder への改善提案**：flow.md・agents・スキルへの具体的な変更案（ファイル名と変更内容まで書く）

改善提案の採否はユーザーが判断し、採用分は Develop Folder 側に反映する（このプロジェクト内では反映しない）。

## Phase 8以降：運用フェーズ

デプロイ後、ユーザーからの不具合修正・機能追加の依頼に個別対応する。

> **【担当】** 依頼の整理・ユーザー確認・progress.md 更新 ＝ メイン ／
> 設計書更新・**README 更新** ＝ `design-writer` ／ 実装 ＝ `implementer` ／ バグ修正 ＝ `debugger` ／
> テスト ＝ `tester` ／ 再デプロイ ＝ `deployer`（承認必須）に委譲

### 1タスクのサイクル（この順序を崩さない）

1件のタスク（バグ修正・機能追加・設定変更など）は必ず次の7ステップを1セットで回す。
**ステップ5・6を飛ばして7に進むことは禁止**（README・progress.md が古く取り残される原因はここ）。

```
1. 依頼の整理・変更カテゴリの確定（メイン）
2. 設計書の更新 → ユーザー承認（design-writer に委譲。絶対ルール1・3）
     該当する writer 系スキル（requirements-writer 等）で既存ファイルへの追記・部分修正として行う
     （ゼロから作り直さない。既存のFR番号・ERR番号は変えない）
3. 実装（implementer / バグ修正は debugger に委譲）
4. テスト（tester に委譲）
5. README の更新判定と反映 ★省略不可
     「README の最新化ルール」の更新トリガー表に照らす
     ├─ 1つでも該当 → design-writer に委譲して該当セクションを差分更新
     │                （readme-writer → humanizer-ja。完成後メインがユーザーに提示）
     └─ 該当なし   → 「該当なし」と判断した根拠をユーザーに一言伝える（黙って飛ばさない）
6. progress.md の更新（メイン）
     - 「直近の決定事項」に日付・内容を1行追記する
     - 「実装済み」リストに変更があれば反映する
     - 「README 最新化」欄を更新する（更新した／該当なしと判断した旨を記録）
     - 「次のアクション」を空欄化する（未完タスクが残っていればそのまま残す）
7. コミットと同期
     - README ドリフト検出 hook の警告が出たら 5 に戻る
     - main への Push はユーザー承認を得る
     - 夜間・クラウド作業は `codex/*` にコミットし、継続許可がある場合だけ Push・PR 作成まで行う
```

個々のタスクは「フェーズ開始」でも「設計書完成」でもないため見落としやすい。
Phase 8に入った後は、上記1〜7を必ずワンセットで扱うこと。
「実装とテストが終わったからタスク完了」ではない（README 反映と progress.md 更新まで含めて完了）。
